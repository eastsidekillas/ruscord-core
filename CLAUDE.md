# Инструкции для работы в репозитории

## Перед началом любой задачи
1. Прочитай `docs/README.md`, затем `docs/roadmap.md` (где мы сейчас) и последние
   записи `docs/devlog.md` (что делали и что осталось открытым).
2. Если задача касается решения из `docs/adr/`, прочитай этот ADR и проверь его
   триггеры пересмотра.

## В каждом PR
- Тесты на новую логику. Права (`internal/perm`) и протокол gateway без табличных
  тестов не мержатся.
- Запись в `docs/devlog.md`: что сделано, что узнали, что осталось открытым.
- Если решение изменилось или появилось новое, отдельный ADR (шаблон
  `docs/adr/0000-template.md`). Старые ADR не переписываются: им ставится статус
  «заменён ADR-NNNN».
- Пройди `docs/review-checklist.md` и отметь в описании PR, какие пункты затронуты.
- Новое допущение без проверки попадает в `docs/assumptions.md`.

## Коммиты, ветки, PR
- Ветки без префиксов инструментов, по смыслу: `step-2-auth`, `fix-refresh-race`.
- В сообщениях коммитов нет строк `Co-Authored-By` и ссылок на сессии, автор
  коммита — аккаунт владельца репозитория.
- В описании PR нет футера «Generated with …» и ссылок на сессии.

## Правила кода
- Модули в `internal/` общаются через интерфейсы и события, не через чужие таблицы.
- Код чистый, без дублирования. Логику, которая встречается во второй раз,
  выносим в общую функцию: внутри пакета в его хелперы, между пакетами в
  `internal/platform/...`. Это касается и тестов (общая обвязка БД, клиенты).
- Секреты только из env. В dev всё слушает 127.0.0.1.
- Комментарии в коде на английском, документация на русском.
- Команды: `make test`, `make lint`, `make up`, `make run`; `make test-docker` —
  тесты с Postgres 18 и линтер в Docker, как в CI, без локального Go.
