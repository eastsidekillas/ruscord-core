# План шага 6: голосовые комнаты и показ экрана

Статус: **в работе**. Решения владельца — в конце; технические решения —
ADR-0025.

## Зачем

Узкий сценарий из [product/positioning.md](../product/positioning.md) (ADR-0024):
компания друзей пишет, заходит в голосовую комнату одним действием и
показывает экран. Владелец проверяет его с друзьями и выносит вердикт.

## Что уже есть

- **ADR-0001.** Self-hosted LiveKit. Ядро говорит с ним только из модуля
  `voice`, клиент — через обёртку `VoiceEngine`.
- **ADR-0007.** Комната голосового канала — `voice:<channel_id>`, звонка —
  `call:<call_id>`. Токен на вход живёт 60 с.
- **`perm.Voice(p)`** уже переводит права канала в грант LiveKit:
  - `CONNECT` → вход;
  - `SPEAK` → микрофон;
  - `VIDEO` → камера;
  - `STREAM` → экран и звук экрана;
  - `STREAM_HQ` → экран выше 720p;
  - без `USE_VOICE_ACTIVITY` — только push-to-talk.

  Есть табличные тесты.
- **Окружение.** LiveKit в docker compose (`livekit-server:v1.13.10`),
  ключи из `.env`, роль процесса `voice` в конфиге.
- **Нет:** модуля `voice` в коде, `livekit-client` в клиенте, кнопок голоса.

## Что говорит документация LiveKit (проверено 2026-11-01)

- **Токен.** JWT: `iss` — ключ API, `sub` — личность участника, `nbf`/`exp`,
  `metadata`. В объекте `video` — `roomJoin`, `room`, `canPublish`,
  `canPublishSources` (`camera`, `microphone`, `screen_share`,
  `screen_share_audio`), `canSubscribe`, `canPublishData`,
  `canUpdateOwnMetadata`, `roomAdmin`.
  - **Важно:** `exp` действует только на первое подключение, а не на
    переподключения
    ([Tokens & grants](https://docs.livekit.io/frontends/reference/tokens-grants.md)).
- **RoomService.** HTTP `POST /twirp/livekit.RoomService/<Метод>`, тело
  JSON, `Authorization: Bearer <токен с roomAdmin>`. Нужные методы:
  `ListParticipants`, `RemoveParticipant`, `MutePublishedTrack`,
  `UpdateParticipant`.
  - Смена прав участника отзывает его текущий токен.
  - Удалённо включить микрофон по умолчанию нельзя
    ([Room service API](https://docs.livekit.io/reference/other/roomservice-api.md)).
  - `revoke_token_ts` у `RemoveParticipant` есть только в LiveKit Cloud.
- **Вебхуки.** Секция `webhook` (`api_key`, `urls`); POST с JSON,
  `Content-Type: application/webhook+json`, в `Authorization` — JWT с
  sha256 тела. События `participant_joined`, `participant_left`,
  `room_finished`, `track_published`.
  - Доставка **не гарантирована**; есть повторы, порядок сохраняется
    ([Webhooks & events](https://docs.livekit.io/intro/basics/rooms-participants-tracks/webhooks-events.md)).

## Как сделать

### Объём

| Часть | Что | Для сценария |
|---|---|---|
| **6a** | Голосовые каналы серверов: вход, выход, mute/deafen, кто в комнате и кто говорит, серверный mute и отключение модератором, переподключение | да |
| **6b** | Показ экрана в голосовом канале: старт, стоп, просмотр, индикатор «вы показываете экран» | да |
| 6c | Звонки в личках и группах (`call:<id>`, «звонит», принять или отклонить) | да, до проверки (решение 2026-11-01) |
| 6d | Камера | да, до проверки (решение 2026-11-01) |
| — | Push-to-talk вне вкладки, шумоподавление Krisp, запись, E2EE | не сейчас: шаг 7–8 или платное |

Шумоподавление: включаем встроенное в браузер (`noiseSuppression`,
`echoCancellation`). Оно бесплатное и есть везде.

### Ядро (модуль `voice`)

1. **Вход.** `POST /channels/{id}/voice` проверяет `perm.Voice` и
   `user_limit` и выдаёт `{url, token}`.
   - Токен на 60 с, `sub` = id пользователя.
   - Имя и аватар ставит сервер (`metadata`), `canUpdateOwnMetadata = false`.
   - `roomAdmin` клиент не получает никогда.
   - Из прошлой комнаты пользователь выводится (`RemoveParticipant`): на
     сервере одна голосовая комната на пользователя, как в Discord.
2. **Кто в комнате.** Правда о том, кто в комнате, — у LiveKit. Ядро узнаёт
   её из вебхуков `participant_joined` и `participant_left`:
   - пишет `voice_state` в Valkey (TTL);
   - рассылает `VOICE_STATE_UPDATE` по эфемерному пути (ADR-0018);
   - кладёт голосовые состояния сервера в `GUILD_CREATE` и READY.

   Вебхук может потеряться, поэтому раз в минуту — сверка через
   `ListParticipants` по комнатам, где есть состояния.
3. **Права в разговоре.** Кик, бан, выход с сервера, потеря `CONNECT` или
   `VIEW_CHANNEL` → `RemoveParticipant`. Потеря `SPEAK` или `STREAM` →
   `UpdateParticipant` с новыми источниками.
   - Переподключение после кика: `exp` не действует на переподключения, а
     отзыв токена по времени есть только в Cloud. Поэтому на
     `participant_joined` ядро снова проверяет права и выводит того, кому
     нельзя. Окно — до прихода вебхука.
4. **Модерация.**
   - `MUTE_MEMBERS` → `MutePublishedTrack` для микрофона и флаг в состоянии.
   - `MOVE_MEMBERS` → отключение из комнаты (переноса в LiveKit нет). Клиент
     получает событие и заходит в новую комнату с новым токеном.
5. **Вебхуки.** Приём на ядре с проверкой подписи (JWT + sha256 тела, тот же
   ключ API). В compose — `webhook.urls: [http://core:8080/...]`.
6. **Реализация.** Официальный Go SDK LiveKit (`server-sdk-go`, Apache 2.0)
   или своя тонкая обёртка: JWT уже подписываем `golang-jwt`, RoomService —
   это JSON по HTTP. Выбор — в ADR-0025 после проверки размера
   зависимостей SDK.

### Клиент

- **`livekit-client`** (npm, Apache 2.0) за обёрткой `VoiceEngine`: в
  компонентах нет прямых вызовов SDK.
- **Вход.** Клик по голосовому каналу — вход. Под каналом — участники:
  аватар, имя, иконки mute/deafen, рамка «говорит».
- **Панель соединения внизу,** пока вы в голосе: где вы, качество связи,
  микрофон, звук, экран, выйти. Она видна на любом экране, пока соединение
  активно.
- **Показ экрана.** `getDisplayMedia` через SDK. Пока вы показываете экран,
  виден индикатор и кнопка «Остановить». Чужой экран открывается в центре
  по клику на значок у участника.
- **Ошибки показываем, а не прячем:** нет доступа к микрофону, браузер
  запретил показ экрана, переподключение, вас отключил модератор.
- **Права.** Кнопок нет, если права нет (`GUILD_PERMISSIONS_UPDATE` уже
  приходит). Отказ всё равно решает сервер.

### Тесты

- **Ядро:**
  - табличные тесты гранта и токена (claims, источники, TTL);
  - проверка подписи вебхука;
  - сверка состояний;
  - вывод из комнаты при кике, бане и смене прав — на фейковом RoomService
    (httptest).
- **Интеграция в CI.** В compose уже есть LiveKit. e2e (`e2e/ci.sh`):
  два браузера с фейковыми микрофонами входят в голосовой канал и видят
  друг друга.
  - Входящий звук проверяем по статистике WebRTC, а не на слух.
  - Флаги Chromium `--use-fake-device-for-media-stream` и
    `--use-fake-ui-for-media-stream`. Как в headless автоматически выбрать
    экран для `getDisplayMedia`, **проверить** при реализации 6b.
- **Сети** (NAT, мобильный интернет, TURN) локально не проверить: нужен
  staging (допущение A4).

## Без чего с друзьями не проверить

1. **Сервер с публичным IP.** Друзья не подключатся к вашему localhost.
   ADR-0008: один регион, провайдер в РФ, если аудитория в РФ.
   Ориентир из architecture.md для LiveKit: 4–8 vCPU, 8 ГБ, канал от
   1 Гбит/с. Для пары компаний друзей хватит меньшего — это замерим.
2. **Домен и TLS.** Браузер даёт микрофон и показ экрана только по HTTPS
   (кроме localhost).
3. **TURN** (встроенный в LiveKit) на 443/TLS и 3478/UDP — для тех, у кого
   строгий NAT или корпоративная сеть.
4. **Телефоны.** Если друзья зайдут с телефона, сейчас клиент там не
   работает (audit/mobile-2026-11-01.md).

## Порядок

6a ядро → 6a клиент → 6b экран → staging → проверка с друзьями → по
вердикту 6c/6d или раскладка для телефона.

## Решения владельца (2026-11-01)

1. **Камера** — до проверки с друзьями.
2. **Звонки в личках** — до проверки.
3. **Сервер** — VPS с доменом или домашний сервер. Домашний подходит, только
   если провайдер даёт белый IP и можно пробросить порты, включая UDP для
   медиа. За CGNAT друзья не подключатся.
4. **Телефоны** — скорее нет, раскладку для узкого экрана делаем позже.
