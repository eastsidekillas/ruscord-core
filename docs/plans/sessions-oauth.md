# План: управление сессиями и вход через внешние аккаунты

Статус: часть 1 — **принята** и в работе (ADR-0023); часть 2 — **проект**,
решения владельца в конце.

Зачем:
- открытые пункты аудита безопасности
  ([audit/security-2026-10-31.md](../audit/security-2026-10-31.md)):
  - O1 — после выхода токен ещё до 10 минут работает;
  - O2 — нет списка устройств, «выйти везде» и смены пароля;
- требование закона к способам входа ([legal/russia.md](../legal/russia.md), L5).

## Что уже есть

- **Сессия.** Строка `sessions` — одно устройство, одна «семья»
  refresh-токенов (ADR-0009).
- **Поля сессии:** `device` (User-Agent), `ip` при входе, `created_at`,
  `last_used_at` (обновляется при каждом refresh, то есть не реже раза в
  10 минут у активного клиента), `expires_at` (30 дней с последнего
  refresh), `revoked_at` и `revoke_reason`.
- **Отзыв сессии** (`revokeSession`) в той же транзакции шлёт
  `SESSION_REVOKE`, и gateway сразу закрывает соединения этой сессии.
- **REST не проверяет отзыв:** access-JWT без запроса в базу живёт до
  10 минут.
- **Повторный ввод пароля** уже есть у удаления аккаунта.

## Часть 1. Управление сессиями

Не зависит от внешних провайдеров. Делаем первой.

### API

| Метод | Что делает |
|---|---|
| `GET /users/@me/sessions` | Активные сессии: `id`, `device` (браузер и ОС, разобранные из User-Agent), `ip`, `created_at`, `last_used_at`, `current: true` у текущей |
| `DELETE /users/@me/sessions/{id}` | Завершить одну сессию; свою текущую — то же, что выход |
| `POST /users/@me/sessions/revoke-others` | «Выйти на всех других устройствах»; нужно подтверждение (см. ниже) |
| `POST /users/@me/password` `{current_password, new_password}` | Сменить пароль; все другие сессии завершаются, текущая остаётся |

Чужая сессия и несуществующий `id` отвечают одинаково — 404, как везде.

### Мгновенный отзыв (закрывает O1)

**Механизм.** При отзыве сессии в Valkey пишется ключ
`revoked:<session_id>` с TTL 11 минут (срок жизни access-токена и запас на
расхождение часов). `RequireAuth` проверяет его одним `EXISTS`, gateway уже
закрывает соединения по `SESSION_REVOKE`. Ключ ставится после коммита
транзакции. Если Valkey недоступен, запрос отклоняется — как у лимитов,
которые тоже в Valkey.

**Цена.** Один запрос в Valkey на каждый REST-запрос (доли миллисекунды по
локальной сети). Gateway и голос по-прежнему проверяют JWT без базы.

**Альтернатива — короче access-токен** (например, 2 минуты). Тогда в 5 раз
больше refresh, а окно не закрывается до нуля. Отвергаем.

### Подтверждение для опасных действий

Для смены пароля, «выйти везде», привязки и отвязки способа входа и
удаления аккаунта нужно недавнее подтверждение личности.

- **Аккаунт с паролем.** Пароль в теле запроса — как сейчас у удаления.
- **Аккаунт без пароля** (только вход через VK или Яндекс). Нужен вход через
  провайдера не раньше 5 минут назад. В сессии хранится
  `authenticated_at`; повторная авторизация у провайдера (`prompt=login` или
  его аналог) обновляет его.

Иначе тот, кто на минуту получил доступ к открытой вкладке, выкинет
владельца со всех устройств.

### Ещё

- **Лимит сессий.** До 100 активных на пользователя. Сверх лимита
  завершается самая давно не использованная — защита от раздувания таблицы.
- **«Новый вход».** Событие `SESSION_CREATE` в топик пользователя: другие
  его устройства показывают «Вход с нового устройства: Firefox, Windows,
  IP …». Письмо — когда будет почтовый провайдер (P1).
- **Последний IP.** При refresh обновлять ещё `last_ip`. Сейчас `ip` — только
  адрес входа, а пользователю полезнее последний.
- **Хранение.** Завершённые сессии (IP и время — это метаданные) не
  удаляем, пока юрист не ответит про сроки хранения (legal/russia.md, L2).
  Пользователь видит только активные.

### Клиент

- В настройках аккаунта — раздел «Устройства»: список сессий, у текущей
  пометка «это устройство», кнопка «Завершить» у каждой и «Выйти на всех
  других».
- Смена пароля в настройках аккаунта.
- По `SESSION_REVOKE` своей сессии клиент уже уходит на вход.

## Часть 2. Вход через внешние аккаунты

«OAuth» здесь значит две разные вещи:

1. **Вход в Ruscord через VK ID, Яндекс ID, Сбер ID.** Ruscord — клиент
   OAuth. Это нужно сейчас из-за закона, см. ниже.
2. **Ruscord как провайдер OAuth** для ботов и сторонних приложений
   («Войти через Ruscord», токены со scope, как OAuth2 у Discord). Это P2,
   вместе с ботами (plans/discord-parity.md, §9). Часть 1 к нему готовит:
   сессия станет одним из видов выданного доступа.

Ниже — только первое.

### Что требует закон (проверено 2026-10-31)

**Запрет.** Он введён в 2023 году (406-ФЗ, п. 10 ст. 8 149-ФЗ). Входить на
российские сайты можно:
- по российскому номеру телефона;
- через Госуслуги (ЕСИА);
- через ЕБС;
- через иную российскую систему авторизации — её владелец должен быть
  гражданином РФ без иного гражданства или российским юрлицом.

Примеры таких систем — VK ID, Яндекс ID, Сбер ID.

**Штрафы.** Их ввёл Федеральный закон от 26.06.2026 № 199-ФЗ (ст. 13.55
КоАП), в силе с 07.07.2026: гражданам 10–20 тыс. ₽, должностным лицам
30–50 тыс. ₽, юрлицам 500–700 тыс. ₽
([Гарант](https://www.garant.ru/article/2136195/)).

**Email и пароль.** По разъяснению РОЦИТ, которое приводит Гарант, логин в
виде адреса почты сам по себе не запрещён: запрет касается сервиса, который
подтверждает личность. Это вторичный источник — **вопрос юристу**: можно ли
оставить вход по email и паролю рядом с VK и Яндекс ID или только их.

**Госуслуги** владелец исключил (2026-10-31).

### Провайдеры

| Провайдер | Протокол | Что даёт | Заметки |
|---|---|---|---|
| VK ID | OAuth 2.1 ([VK ID](https://id.vk.ru/about/faq/business/vkid/OAuth/30022)) | id, имя, аватар, подтверждённый телефон | владелец отказался (2026-10-31) |
| Twitch | OAuth 2.0 | — | иностранный (Amazon); см. «Открыто: Twitch» в конце |
| Яндекс ID | OAuth 2.0 ([Яндекс](https://yandex.ru/dev/id/doc/ru)) | id, логин, имя, аватар, email, телефон — по правам приложения | |
| Сбер ID | OAuth 2.0 / OIDC | — | требования к подключению не проверены; позже, если понадобится |

Условия подключения (нужны ли ИП или юрлицо, домен, проверка приложения)
проверить в кабинетах провайдеров при регистрации приложений. Это связано с
L10: оператор ПДн — ИП или юрлицо.

### Модель данных

```sql
CREATE TABLE user_identities (
    user_id    uuid NOT NULL REFERENCES users (id),
    provider   text NOT NULL,          -- 'vk', 'yandex'
    subject    text NOT NULL,          -- the user's id at the provider
    created_at timestamptz NOT NULL DEFAULT now(),
    last_login_at timestamptz,
    PRIMARY KEY (provider, subject)
);
CREATE INDEX user_identities_user ON user_identities (user_id);
```

- **Токены провайдера** (access и refresh VK или Яндекса) не храним: нам
  нужен только факт входа и id, а не доступ к их API. Нечему утекать.
- **Пароль может отсутствовать.** `users.password_hash` становится
  nullable, `users.email` тоже: у аккаунта из VK может не быть почты.
- **Способ входа не должен исчезнуть.** У аккаунта всегда остаётся хотя бы
  один способ входа. Отвязать последний нельзя — проверка в той же
  транзакции.

### Поток входа

Authorization code с PKCE, `state` и `nonce`. Обмен кода на сервере, секрет
приложения — из env.

1. Клиент открывает `GET /api/v1/auth/oauth/{provider}/start?intent=login|link`.
   - Ядро создаёт `state`, `code_verifier` и `nonce` и кладёт их в Valkey на
     10 минут.
   - Ставит куку `rc_oauth` (`HttpOnly`, путь `/api/v1/auth/oauth`) со
     значением, связанным со `state`.
   - Отвечает 302 на провайдера.
2. Провайдер возвращает пользователя на
   `GET /api/v1/auth/oauth/{provider}/callback?code&state`.
   - Ядро сверяет `state` с кукой: защита от подмены входа (login CSRF).
   - Удаляет запись из Valkey: `state` одноразовый.
   - Меняет код на токен и запрашивает id пользователя.
3. Дальше по `(provider, subject)`:
   - **Найдена привязка.** Обычный вход: новая сессия, куки, 302 в
     приложение. Удалённый аккаунт — отказ.
   - **`intent=link` и пользователь вошёл.** Нужно подтверждение (см.
     часть 1). Привязка, событие `USER_UPDATE`.
   - **Привязки нет — регистрация.** Ядро кладёт в Valkey «незавершённую
     регистрацию» на 15 минут. Клиент спрашивает имя пользователя
     (`username`), отображаемое имя подставляется из профиля провайдера.
     Затем `POST /api/v1/auth/oauth/complete` создаёт пользователя, привязку
     и сессию одной транзакцией.

**Без автоматической склейки по email.** Если в Яндексе тот же email, что у
существующего аккаунта, аккаунты не объединяются сами. Иначе захват чужого
аккаунта через провайдера, где почта не подтверждена или сменила владельца.
Привязка — только из уже вошедшего аккаунта (`intent=link`).

**Куда вернуть после входа** — только относительный путь внутри приложения:
защита от открытого редиректа (тот же приём уже есть в `sign-in.ts`).

**Лимиты** — те же, что у входа и регистрации по паролю (по IP).

**Провайдер недоступен.** Вход через него не работает, остальные способы
работают. В `/readyz` провайдеры не входят: их сбой не делает ядро
неготовым.

### Клиент

- **Страница входа.** Кнопки «Войти через VK ID» и «Войти через Яндекс»
  рядом с формой.
- **Новая страница.** «Придумайте имя пользователя» для незавершённой
  регистрации.
- **Настройки аккаунта.** Раздел «Способы входа»: привязать, отвязать
  (кроме последнего), задать пароль аккаунту без пароля.

## Порядок работ

1. **Часть 1: сессии.** Мгновенный отзыв, список, «выйти везде», смена
   пароля, подтверждение опасных действий. Ядро и клиент, тесты (в том числе
   табличные на подтверждение и на чужие сессии), ADR-0023. От решений
   юриста не зависит.
2. **Способы входа.** `user_identities`, nullable пароль и email, поток
   OAuth с фейковым провайдером в тестах (свой httptest-сервер). VK ID и
   Яндекс ID подключаются конфигом, когда владелец зарегистрирует
   приложения.
3. **Телефон** (SMS или звонок) и идентификация через оператора (L4) — после
   ответа юриста.
4. **Ruscord как провайдер OAuth** — с ботами (P2).

## Решения владельца

Ответы от 2026-10-31:

1. **Провайдеры:** Twitch и Яндекс ID. VK — нет («мёртвая площадка»).
   Госуслуги — нет.
2. **Мгновенный отзыв через Valkey** — да (ADR-0023).
3. **Уведомление «новый вход»** — да (ADR-0023).
4. **Направление:** к легализации в РФ, но с путями обхода.

**Открыто: Twitch.** Принадлежит Amazon, то есть иностранная система
авторизации. Вход через неё для пользователей из РФ запрещён (406-ФЗ), с
07.07.2026 за это штраф (199-ФЗ, ст. 13.55 КоАП). Варианты для решения
владельца:
- **A.** Twitch как «подключённый аккаунт» в профиле, без входа через него.
- **B.** Вход через Twitch только вне РФ.
- **C.** Вход через Twitch для всех — с риском штрафа.

Вопрос юристу: подпадает ли под запрет вариант A.

5. Оставляем ли вход по email и паролю — после ответа юриста (вопрос в
   legal/russia.md, L5).
