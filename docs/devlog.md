# Журнал разработки

Новые записи сверху. Формат: что сделали, что узнали, что открыто.

## 2026-10-30 · Шаг 5a: gateway

**Сделано**
- Модуль `internal/gateway` (ADR-0016): `GET /gateway?v=1`, HELLO → IDENTIFY
  или RESUME по тикету → READY → DISPATCH с `s` по порядку, heartbeat с
  подтверждением полученного `s`, коды закрытия 4000–4013 и 1012 (таблица в
  `docs/api.md`). Лимиты: кадр до 4 КиБ, 120 кадров в минуту, 20 сессий
  пользователя на ноду, 10 с на IDENTIFY, 1,5 интервала на heartbeat.
- Доставка: упорядоченный потребитель JetStream на сессию с фильтром по
  топикам пользователя, его серверов и личек; при входе в сервер, выходе, новой
  личке потребитель пересоздаётся сразу после события. Точка старта — последняя
  последовательность стрима, прочитанная до снимка READY.
- Фильтр (`router`): снимок каждого сервера в памяти сессии, обновляется из
  событий. Сообщения сервера — только тем, кто видит канал; приглашения — с
  `MANAGE_GUILD`; смена ролей, переопределений, своего участника или владельца
  даёт `CHANNEL_CREATE`/`CHANNEL_DELETE` ровно для открытых или скрытых каналов.
  Закрыт пункт из шага 4a: `CHANNEL_CREATE` скрытого канала больше никто не видит.
- RESUME: сессия живёт 2 минуты после обрыва и дочитывает события в буфер
  (до 2048 кадров и 2 МиБ, подтверждённые heartbeat'ом освобождаются).
  Продолжить может только та же сессия входа.
- guild: `Snapshot`/`Snapshots` (все каналы, включая скрытые, загрузка
  пятью запросами в одной read-only транзакции), `Snapshot.View` и `Full`;
  `guild.full` для REST теперь строится через них, вычисление прав в канале
  в одном месте (`channelPerm`, `permGuild`).
- auth: `SessionActive`, `ConsumeTicket`; отзыв сессии (выход, повтор
  refresh-токена) пишет внутреннее событие `SESSION_REVOKE`, gateway закрывает
  соединения этой сессии кодом 4004.
- HTTP-сервер получил `ReadTimeout` 30 с и `WriteTimeout` 60 с (пункт из
  аудита). WebSocket они не режут: net/http снимает дедлайны при hijack, это
  закреплено тестом.
- `main`: роль `gateway` собирает те же модули, что и `api`, и регистрирует
  `/gateway`. С `RUSCORD_ROLES=all` (по умолчанию) всё в одном процессе.
- Общая обвязка: `internal/platform/natstest` (встроенный NATS для тестов,
  вынесен из тестов relay); `apitest.User` создаёт настоящую сессию входа,
  `apitest.User.Ticket`, `Env.URL`.
- Тесты: табличные на фильтр (48 случаев, включая «скрытый канал не утекает
  ни названием, ни сообщениями»), на коды закрытия (23 случая), на буфер
  повтора (13); RESUME, в том числе при ещё открытом старом сокете, и отказы в
  нём; отзыв сессии, остановка ноды, медленный клиент, таймауты HTTP; сквозной
  тест REST → outbox → relay → JetStream → WebSocket на Postgres (вход по
  приглашению, скрытый канал, открытие ролью, кик, личка) и закрытие по выходу
  из аккаунта. Проверили, что тесты ловят ошибки: выключение фильтра
  сообщений, диффа видимости, проверки `MANAGE_GUILD`, проверки владельца при
  RESUME и проверки «чьё соединение закрылось» роняют тесты.

**Узнали**
- RESUME «с номера стрима на любой ноде» (план) не работает без знания, что
  клиент видел на момент обрыва: состояние, собранное заново, теряет скрытые
  за время обрыва каналы. Поэтому RESUME на своей ноде, решение и триггер
  пересмотра в ADR-0016.
- Payload `GUILD_CREATE` в outbox без скрытых каналов, а фильтру они нужны,
  поэтому gateway перечитывает сервер при вступлении. Свой `GUILD_MEMBER_ADD`
  идёт в стриме раньше `GUILD_CREATE` и по топику сервера, на который сессия ещё
  не подписана, поэтому не приходит — и не нужен.
- Закрытие старого сокета после RESUME на новом завершало бы уже
  перехваченную сессию; нашлось тестом, теперь закрытие учитывается, только
  если сокет ещё текущий.
- `http.ResponseController` для снятия дедлайнов перед upgrade не нужен: net/http
  делает это сам при hijack. Тест на это остался.
- В этой среде нет доступа к proxy.golang.org: Go 1.26 собран из исходников,
  модули брались напрямую с GitHub. Локальная проверка шла на Postgres 16 (в CI
  18). Тест `TestRegisterLoginMe` падает при локальной таймзоне не UTC:
  регистрация отдаёт `created_at` в UTC, `/users/@me` — в локальной зоне
  процесса (pgx отдаёт timestamptz в `time.Local`).

**Повторный аудит перед мержем (найдено и исправлено; на каждое, кроме
закрытия кодом 1005, есть тест, который падает без исправления — 1005
тестовый клиент отправить не может)**
- Событие стрима с невалидным JSON роняло весь процесс: кодировщик кадра
  паниковал в горутине сессии. Теперь такое событие пропускается с
  предупреждением, а паника в сессии завершает только её (recover, код 4000).
- Старые события из окна между позицией стрима и снимком накладывались на
  свежий снимок. Смесь «старые переопределения канала + новые роли» могла
  открыть канал, который пользователь не видел ни тогда, ни сейчас; сквозной
  тест с отстающим relay это воспроизвёл. Снимок теперь хранит отметку —
  id последнего события сервера в outbox (миграция 00006, индекс
  `outbox (topic, id)`), и события состояния до неё пропускаются (ADR-0016).
- Завершение сессии по окну или вытеснению могло совпасть с RESUME: сессия
  заканчивалась, а новый сокет оставался открытым без событий. Теперь
  завершение сессии всегда закрывает подключённый сокет (4006).
- Оборванные сессии занимали лимит 20 на пользователя 2 минуты, и падающий
  клиент получал 4013 «не переподключаться». Теперь при лимите вытесняется
  самая старая оборванная сессия.
- Heartbeat без поля `d` закрывал соединение (4002); теперь это `null`.
- Если клиент закрыл сокет кодом, который нельзя отправить в ответ (1005),
  сокет закрывается принудительно.
- Живой прогон бинаря (Postgres, redis-server, nats-server 2.15.2) клиентом
  «чёрным ящиком»: REST с cookie и `Origin`, WebSocket, вход по приглашению,
  скрытый канал, RESUME после обрыва сети, закрытие по выходу из аккаунта,
  1012 при остановке; и в одном процессе, и с `RUSCORD_ROLES=api` и
  `RUSCORD_ROLES=gateway` в разных процессах. Нашёл потерю событий: после
  пересоздания базы при живом стриме NATS id outbox повторялись, и relay с
  `Nats-Msg-Id` = id молча терял события 2 минуты (окно дедупликации). Ключ
  теперь id + `created_at`, id outbox едет в заголовке `Ruscord-Outbox-Id`
  (тест `TestRelayNewDatabaseReusesIDs`, повторный живой прогон зелёный).
- `make test-docker` (`scripts/test-docker.sh`): тесты с `-race` на Postgres 18
  из compose и golangci-lint версии CI в контейнерах, лог в `test-docker.log`.
  Нужен, чтобы проверять ветку на машине без Go и Postgres.
- Тестовый `flush` relay ошибочно считал очередь пустой, когда advisory-лок
  (он общий на всю базу) держал relay параллельного теста.

**Открыто**
- Поле `permissions` сервера после смены ролей клиент пересчитывает сам;
  если это неудобно в Angular, gateway может слать готовое значение (решить в 5b).
- Нет read states и голосовых состояний в READY (шаг 6 и далее), нет presence.
- RESUME только на той же ноде (ADR-0016); при остановке ноды кадры
  закрытия могут не успеть уйти: `Shutdown` не ждёт hijack-соединения.
- Сессия входа, истёкшая по `expires_at` без отзыва, не закрывает уже открытое
  соединение (только новые IDENTIFY и RESUME проверяют срок).
- Разница зон `created_at` между регистрацией и `/users/@me` (см. выше) —
  поправить в auth.
- Нагрузочные допущения A14–A16 проверить на шаге 8.
- Лимит на число неавторизованных соединений с одного IP держит только таймаут
  IDENTIFY (10 с); остальное — на reverse proxy перед бетой.
- golangci-lint локально не запускался (сборка под Go 1.26 недоступна в этой
  среде); проверяет CI.

## 2026-10-29 · Аудит ядра перед шагом 5

Прошли весь код main (auth, guild, invites, social, message, events, httpx,
main) и сверили с `docs/api.md`.

**Исправлено**
- User-Agent с битым UTF-8 давал 500 на регистрации и входе: строка уходила в
  `sessions.device` как есть. Ещё длинный UA на кириллице резался по байтам
  посреди символа. Теперь UA чистится от битых байтов и NUL и режется по
  символам до 128.
- Вход с email длиннее 254 символов сразу отвечает `invalid_credentials` и не
  создаёт ключ лимитера произвольной длины в Valkey.
- Заявка в друзья по имени с NUL давала 500. Имя, которое не может
  существовать, теперь сразу «не найдено», ответ тот же `request_failed`.
- `topic` канала пропускал NUL (500): переведён на `Fields.Length`.
- Удаление роли оставляло её переопределения в каналах навсегда. Теперь они
  удаляются вместе с ролью, а при кике или выходе удаляются переопределения
  участника, и в обоих случаях уходит `CHANNEL_UPDATE` по каждому каналу.
  Раньше клиенты не узнавали об изменении.
- `ADMINISTRATOR` в переопределении канала отвечает 422: в канале этот бит
  ничего не значит, а раньше его можно было сохранить.
- `max_age` приглашения около 9e18 переполнял умножение на секунды. Теперь
  диапазон проверяется до умножения, ответ 422.
- `PATCH /guilds/{id}/members/@me` с пустым телом отвечал 204 даже не
  участнику, то есть выдавал, что сервер существует. Теперь 404.
- `GET /guilds/{id}` отдавал `member` без `user`, хотя в списке участников он
  есть. Добавили.
- Ошибки разбора JSON больше не пересказывают внутренности декодера: пустое
  тело, неверный тип поля, неизвестное поле и битый JSON дают понятный текст
  на русском, тело больше 1 МиБ отвечает 413 `body_too_large`.
- Текст `not_text_channel` теперь подходит и для чтения истории, а не только
  для отправки (замечание из ручной проверки 4c-2).
- Чистота кода: разбор `limit` и id из query вынесен в `httpx.QueryUUID` и
  `httpx.QueryLimit` (были копии в участниках и истории сообщений). Удалена
  обёртка `parseUUID` в auth, роуты приглашений в общей таблице.

**Узнали**
- Go-клиент и сервер не пропускают NUL в заголовках, но байты 0x80–0xFF
  проходят. Значит, всё, что приходит из заголовков, нужно чистить так же,
  как поля JSON.
- Ошибки с одной стороны модуля (роль) легко оставляют мусор в соседней
  таблице (переопределения). Каскад в БД здесь не подходит, потому что
  клиентам нужно событие, поэтому удаление идёт через одну функцию
  `dropOverwrites`.

**Открыто (не исправляли, решим позже)**
- `checkGuildCount` не защищён от гонки: два одновременных входа в разные
  серверы могут превысить лимит на один. Нужна блокировка по пользователю,
  решим вместе с банами.
- Списки личек, связей и входящих заявок отдаются целиком, без пагинации.
  Лимиты (1000 друзей) ограничивают размер, но READY в gateway нужно будет
  проверить на объём.
- `position` каналов не ограничена и может повторяться; порядок держится на
  `(position, id)`. Нужен отдельный эндпоинт перестановки.
- У HTTP-сервера нет `ReadTimeout`, только заголовки. Решим на шаге 5 вместе с
  WebSocket, чтобы не порвать долгие соединения.
- Пустой PATCH сервера или канала всё равно пишет событие UPDATE.
- Сообщения от разных отправителей могут попасть в NATS не в порядке id:
  отправки не сериализуются. Клиент сортирует по id (записано в api.md).
- Кикнутый может вернуться по приглашению: банов пока нет.

## 2026-10-29 · Шаг 4c-2: сообщения

**Сделано**
- Модуль `internal/message` (ADR-0015), миграция `00005`: отправка с `nonce`,
  история с курсорами `before`/`after`, правка своих, удаление своих или с
  `MANAGE_MESSAGES`, ответы (`reply_to`), флаг `mention_everyone` по праву.
- Права берутся у владельцев каналов через интерфейсы:
  `guild.ChannelPermissions` и `social.Permissions`. Один путь
  `/channels/{id}/messages` для серверов и личек.
- `hooks.ChannelsDeleted`: сообщения удаляются в той же транзакции, что и канал,
  сервер или группа; guild и social не знают о модуле сообщений.
- Мелочь из ручной проверки 4c-1: личка с самим собой отвечает 400 `self`,
  как и заявка в друзья себе.
- `httpx.Fields.Length` запрещает символ NUL: раньше `"\u0000"` в любом
  текстовом поле давал 500 от Postgres, теперь 422. Проверка регистрации
  переведена на тот же хелпер.
- Тесты: история и курсоры, повтор nonce, чужой nonce, права (только чтение,
  без истории, скрытый канал, `MANAGE_MESSAGES`), лички с блокировкой, топики
  событий, удаление сообщений вместе с каналом, сервером и группой, лимит.

**Узнали**
- NUL нашёлся при написании теста на длинное сообщение: строка из нулевых
  рун прошла бы проверку длины, если бы была короче лимита. Это касалось всех
  модулей, поэтому проверка в общем хелпере, а не в сообщениях.
- `after` удобнее отдавать в том же порядке, что и обычную историю (новые
  первыми), иначе клиенту нужны две ветки рендера.

**Открыто**
- Нет вложений, реакций, упоминаний пользователей и ролей, закреплённых сообщений.
- Нет read states (прочитано до), их отдаст READY в gateway (шаг 5).
- Отправка не берёт блокировку сервера: сообщение, отправленное в миллисекунды
  отзыва права, пройдёт (осознанно, ADR-0015).

    `NoContent`, `PathUUID`; `auth.UserID`, `auth.Attach`, `slicex.Ptrs`;
  - `internal/platform/apitest`: обвязка интеграционных API-тестов (окружение,
    тестовые пользователи, JSON-клиент, список событий outbox). Тесты guild
    переведены на неё.
- Тесты: заявки, отклонение, удаление, встречные заявки одновременно,
  невидимость блокировки (ответ совпадает с ответом на несуществующее имя),
  лички (повторное открытие, общий сервер, блокировка, права `InDM`), группы
  (только друзья, владелец, передача владения, лимит 10).
- CI: два пользователя дружатся и открывают личку через поднятый стек.

**Узнали**
- Встречные заявки в одну и ту же миллисекунду без блокировки пары дали бы две
  исходящие заявки и ни одной дружбы. Advisory lock на ключ пары решает это без
  отдельной таблицы пар.
- Ответ на заявку заблокировавшему должен совпадать не только кодом, но и
  текстом с ответом на несуществующее имя, иначе блокировку видно по сообщению.

**Открыто**
- Нет настроек приватности: любой участник общего сервера может написать в личку.
- Лички нельзя скрыть из списка («закрыть»), как в Discord.
- Presence и «общие серверы» в профиле появятся вместе с gateway (шаг 5).

## 2026-10-29 · Исправление: приглашение в канал, скрытый после создания

**Сделано**
- Превью и вход по приглашению проверяют, что новичок (только @everyone)
  видит канал приглашения. Если канал скрыли после создания приглашения,
  код отвечает 404 и не раскрывает название канала. Когда канал снова открыт,
  приглашение снова работает.
- `loadAccess` разделён на загрузку прав сервера и участника, чтобы считать
  права ещё не вступившего пользователя без копирования кода (`newcomerAccess`).

**Узнали**
- Ручная проверка на Mac нашла то, что тесты пропустили: права проверялись
  только при создании приглашения, а не при каждом использовании. Правило:
  проверка прав живёт там, где объект используется, а не только где создаётся.
  Добавил это в чек-лист ревью.

**Открыто**
- Участник с ролью, которая видит скрытый канал, тоже получит 404 на превью
  такого приглашения: оно никого не впустит, поэтому честно считается мёртвым.

- Мелочи из ручной проверки Тимофея: у ошибок @everyone свой текст на
  переименование, удаление и выдачу; `created_at` при регистрации обрезается
  до микросекунд и совпадает с тем, что потом читается из базы.
- Новое правило в `CLAUDE.md` и чек-листе ревью: без дублирования кода. Сразу
  вынесли повторы: `internal/platform/testdb` (обвязка Postgres для всех
  интеграционных тестов), `httpx.Validation`, общий запрос участников,
  `attachUsers` для любых объектов с id пользователя, `overwritesOf`.
- Тесты: приглашения (лимит использований, срок, права на создание и отзыв,
  скрытый канал, повторный вход), перебор кодов упирается в 429, тексты ошибок
  @everyone, relay (порядок, повтор без дублей, чужой lock, пробуждение по
  NOTIFY) на встроенном nats-server.

**Узнали**
- Порядок блокировок важен: вход по приглашению сначала берёт сервер, потом
  строку приглашения, как и удаление приглашения. Обратный порядок в одном из
  путей давал бы взаимную блокировку.
- `SKIP LOCKED` для параллельных relay ломает порядок событий внутри сервера.
  Глобальный порядок не нужен, а внутри сервера его даёт блокировка ADR-0012.
- Прошлый тест регистрации не мог поймать наносекунды: тестовые часы были
  обрезаны до секунды. Теперь тест сдвигает часы на 123456789 нс.

**Открыто**
- Нет банов: кикнутый участник может вернуться по любому живому приглашению.
- Просроченные приглашения не удаляются, только перестают работать.
- Опубликованные события пока никто не читает: потребитель появится в gateway
  на шаге 5, там же фильтрация по правам (`INVITE_*` только для `MANAGE_GUILD`).
- Перед мержем проверить в compose, что relay создаёт стрим и публикует.

## 2026-10-29 · Шаг 4a: серверы, каналы, роли, участники

**Сделано**
- Миграция `00002`: `guilds`, `roles`, `members`, `member_roles`, `channels`
  (гильдийные и под будущие лички, CHECK на соответствие типа и `guild_id`),
  `permission_overwrites`, `outbox`.
- `internal/events`: типы событий, топики `guild.<id>` и `user.<id>`, запись в
  outbox в транзакции изменения.
- `internal/guild`: REST для серверов, каналов, переопределений прав, ролей и
  участников (`docs/api.md`). Все записи сериализуются блокировкой строки
  сервера и проверяют права в той же транзакции (ADR-0012).
- `auth.Service.Users` отдаёт публичные профили, guild читает пользователей
  только через него.
- `perm.Permissions` сериализуется в JSON строкой, чтобы 64-битные маски не
  ломались в JavaScript.
- 6 интеграционных тестов: 404 для не-участника на каждом маршруте, скрытый
  канал отвечает 404, а видимый без прав 403, переопределения не дают выдать
  чужие биты, иерархия ролей при выдаче, перемещении, удалении и кике,
  непрерывность позиций, неудачные запросы не пишут событий.

**Узнали**
- Переопределение на собственную роль модератора тут же даёт ему эти биты в
  канале, и он может их снять. Так же работает Discord, но в тесте это
  выглядело как дыра; поведение оставили и записали.
- `FOR UPDATE` на `guilds` блокировал бы вставки участников и каналов через
  внешний ключ (`FOR KEY SHARE`). Взяли `FOR NO KEY UPDATE`.
- Создание роли на позиции 1 при проверке «ниже высшей роли» надо сравнивать с
  позицией 0: после сдвига новая роль окажется ниже любой существующей.

**Открыто**
- Gateway обязан фильтровать события `guild.<id>` по правам получателя, иначе
  `CHANNEL_CREATE` скрытого канала увидят все (шаг 5).
- Нет лимитов частоты на создание серверов, каналов и ролей; пока держат только
  количественные лимиты (100 серверов, 500 каналов, 250 ролей). Добавить с 4b.
- Не-участник может на миг взять блокировку сервера (проверка членства после
  блокировки). Безвредно, но при злоупотреблении проверять членство до неё.
- Нет смены ника другим (`MANAGE_NICKNAMES`), передачи владения, банов, аудита.
- При удалении категории каналы теряют `parent_id` (FK `SET NULL`), а события
  `CHANNEL_UPDATE` для них не пишутся. Клиенту придётся перечитать каналы.
- Права считаются из Postgres на каждом запросе без кеша (допущение A11).

## 2026-10-29 · Шаг 2: схема БД и аутентификация

**Сделано**
- Миграции на goose, встроены в бинарь (`migrations/`). В dev применяются при
  старте, в остальных окружениях командой `ruscord migrate`.
- Таблицы `users` и `sessions` (citext для email и username, CHECK на длины).
- `internal/auth`: регистрация, вход, ротация refresh с окном 30 с и отзывом
  сессии при повторном использовании, выход, `/users/@me`, одноразовые тикеты
  для gateway в Valkey (30 с, `GETDEL`).
- `internal/ratelimit`: фиксированное окно на Valkey (`SET NX EX` + `INCR`,
  ключ всегда с TTL).
- `httpx`: единый формат ошибок, разбор JSON с лимитом 1 МиБ и запретом
  неизвестных полей, recover, проверка `Origin`.
- Тесты: 17 в `internal/auth` (unit + интеграционные на настоящем Postgres,
  каждая в своей схеме), лимитер на miniredis. В CI добавлен Postgres-сервис и
  сквозная проверка регистрации через поднятый compose-стек.
- `docs/api.md` с описанием эндпоинтов для фронта.

**Узнали**
- Две вкладки обновляют токен одновременно часто, поэтому строгая ротация без
  окна разлогинивала бы пользователей. Окно 30 секунд закрывает гонку и всё
  ещё ловит украденный токен.
- Лимит попыток на email защищает от перебора, но даёт злоумышленнику
  держать чужой аккаунт в 429 (допущение A9).
- Argon2id на 64 МиБ без ограничения параллельности позволил бы забить память
  сервера пачкой логинов; поставили семафор на 4 хеша.

**Открыто**
- `ClientIP` берёт адрес соединения. За reverse proxy нужен список доверенных
  прокси, иначе лимиты по IP будут общими для всех.
- Access-токен остаётся рабочим до 10 минут после отзыва сессии (осознанно, ADR-0009).
- Нет подтверждения email и восстановления пароля: нужен почтовый провайдер,
  решить до открытой беты.
- Админка и управление сессиями (список устройств, «выйти везде») позже.
