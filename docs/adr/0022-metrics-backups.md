# ADR-0022: Метрики и бэкапы

- Статус: принято
- Дата: 2026-10-31

## Контекст
Аудит 2026-10-31, F4: нет метрик, алертов и бэкапов. На бете без них не узнать
о падении и не восстановиться после потери диска. Сеть этой среды не даёт
скачать новые зависимости (`prometheus/client_golang` тянет protobuf), а
формат Prometheus — несколько строк текста.

## Решение
**Метрики.** Свой маленький пакет `internal/platform/metrics` без зависимостей:
счётчики и гистограммы по меткам, датчики, которые читаются при сборе, формат
Prometheus text 0.0.4. Отдаётся `GET /metrics` **на отдельном адресе**
`RUSCORD_METRICS_ADDR` (по умолчанию `127.0.0.1:9090`, `off` — выключить),
никогда не через публичный прокси. Набор:
- `ruscord_http_requests_total{route,code}` и
  `ruscord_http_request_duration_seconds{route}` — маршрут это шаблон ServeMux
  (`GET /api/v1/guilds/{guild}`), не путь: id в метках дали бы ряд на объект;
- `ruscord_outbox_backlog`, `ruscord_outbox_oldest_age_seconds` — отставание
  relay (стрим событий стоит → клиенты не получают событий);
- `ruscord_gateway_sessions`, `ruscord_blob_garbage_due`;
- `go_goroutines`, `go_memstats_heap_alloc_bytes`, время старта, версия.

**Бэкапы.** `scripts/backup.sh`: `pg_dump -Fc` в каталог с меткой времени UTC
и контрольной суммой; файлы S3 копирует само ядро (`ruscord files-backup DIR`)
в общий каталог `files/` — ключи по содержимому, файл по ключу не меняется,
поэтому каждый запуск докачивает только новые. Хранится 7 последних дампов
(`RUSCORD_BACKUP_KEEP`). `scripts/restore.sh` проверяет сумму и
восстанавливает в рабочую базу (с файлами) или в отдельную базу для проверки
бэкапа. CI делает бэкап и восстанавливает в проверочную базу на каждом PR.

## Альтернативы
- **`prometheus/client_golang`.** Стандарт, но новые зависимости, которых
  здесь не скачать; нам нужна десятая часть его возможностей. Перейти можно без
  изменения имён метрик.
- **Метрики на публичном порту.** Раскрывают маршруты и нагрузку всем.
- **Бэкап файлов через `aws s3 sync` в отдельном образе.** Ещё один образ с
  версией, которую не проверить отсюда; ядро уже умеет говорить с S3.
- **Снимки дисков у хостинга.** Хорошее дополнение на staging, но не
  проверяется в CI и зависит от провайдера.

## Последствия
- Файлы, удалённые сборщиком, остаются в `files/` бэкапа: каталог только
  растёт. При восстановлении такие файлы окажутся в хранилище без ссылок и без
  строки в `blob_garbage`; это место, не ошибка.
- Алерты (Prometheus + Alertmanager или аналог) и вывоз бэкапов на другой
  сервер — часть staging (шаг 8): без второго сервера бэкап на том же диске не
  спасает от потери диска.

## Пересмотреть, если
Понадобятся метрики с высокой кардинальностью или трассировка — тогда
OpenTelemetry.
