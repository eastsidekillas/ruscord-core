# ADR-0011: Модель прав

- Статус: принято
- Дата: 2026-10-29

## Контекст
Права нужны трём модулям сразу: REST (можно ли действие), gateway (кому
отправлять событие), voice (что положить в токен LiveKit). В старом проекте
доступ определялся членством в M2M `participants`, и любой участник мог
удалить сервер.

## Решение
- Права — битовая маска `uint64` в `internal/perm`. Позиции битов хранятся в БД
  и никогда не меняются; тест `TestBitValuesAreStable` ловит сдвиг.
- Модуль чистый: на вход данные гильдии, участника и переопределения канала,
  на выход маска. Загрузку данных делает вызывающий модуль.
- Порядок: `@everyone` → все роли участника → роли целиком → переопределение
  участника. Внутри уровня allow побеждает deny, следующий уровень побеждает
  предыдущий. Владелец и `ADMINISTRATOR` получают всё и не ограничиваются
  переопределениями.
- Неявные правила: без `VIEW_CHANNEL` ничего; без `SEND_MESSAGES` нет вложений и
  упоминаний всех; без `CONNECT` нет голосовых прав; без `STREAM` нет `STREAM_HQ`.
- Иерархия: действовать над участником можно только с более высокой верхней
  ролью; выдавать роль можно только ниже своей и только с правами, которые есть
  у себя.
- Личные сообщения: фиксированный набор для получателей, при блокировке только
  чтение истории.
- `perm.Voice` переводит права в грант LiveKit; права администратора комнаты
  клиентам не выдаются.

## Альтернативы
RBAC через таблицу «роль-право» (гибче, но дороже на каждом запросе и сложнее
кешировать); ACL на каждый канал без ролей (не масштабируется на большие
серверы).

## Последствия
Права вычисляются за микросекунды и кешируются вместе с данными гильдии.
Новое право добавляется только в конец, со строкой в golden-тесте.

## Пересмотреть, если
Понадобятся временные ограничения (тайм-ауты участников) или права на треды:
расширяем входные данные, а не порядок вычисления.
