# ADR-0034: LiveKit Cloud как второй способ подключения

- Статус: принято
- Дата: 2026-11-03

## Контекст

Владелец просит добавить LiveKit Cloud как альтернативу, сохранив
локальный LiveKit.

Что известно:
- **API.** RoomService в LiveKit Cloud — тот же Twirp API
  (`/twirp/livekit.RoomService/<метод>`) с теми же правами (`roomAdmin`,
  `roomList`, `roomCreate`). Документация «Room service API» не различает
  облако и свой сервер.
- **Вебхуки Cloud** настраиваются в панели: «Settings → Webhooks», URL и
  «Signing API key». Подпись — JWT с sha256 тела, как у своего LiveKit;
  ядро уже так проверяет (ADR-0025). Доставка не гарантирована, есть
  повторы (документация «Webhooks & events», проверено 2026-11-03).
- **В ядре** уже есть `RUSCORD_LIVEKIT_URL` (серверный API) и
  `RUSCORD_LIVEKIT_PUBLIC_URL` (куда подключаются браузеры).
- **Сверка ядра** (ADR-0025) смотрит все комнаты LiveKit. Участника комнаты
  с незнакомым каналом или звонком ядро выводит (`VoiceJoined`,
  `CallJoined` возвращают «нельзя»).
- **CSP клиента** разрешает подключения только к своему origin.

## Решение

1. **Переключатель** `RUSCORD_LIVEKIT_MODE=local|cloud` в `.env`; по
   умолчанию `local`. Makefile при `cloud` добавляет
   `deploy/livekit-cloud.yml` и к локальному стеку, и к тестовому серверу.
2. **В режиме cloud:**
   - локальный LiveKit не запускается (профиль, который никто не включает);
   - ядро ходит в `RUSCORD_LIVEKIT_CLOUD_URL`, браузеры подключаются туда же
     напрямую;
   - ключ и секрет — проекта Cloud, в тех же `RUSCORD_LIVEKIT_API_KEY` и
     `RUSCORD_LIVEKIT_API_SECRET`.
3. **Вебхук снаружи — только в режиме cloud.** На тестовом сервере Caddy
   отдаёт ядру один путь, `POST /livekit/webhook`. Его выбирает
   `livekit-cloud.caddy` (`livekit-local.caddy` пустой). Это дополняет
   п. 6 ADR-0025: с локальным LiveKit вебхук по-прежнему не виден снаружи.
   Неподписанный запрос ядро отклоняет (401).
4. **CSP клиента**: nginx — шаблон, `RUSCORD_CSP_CONNECT` добавляет
   `https://*.livekit.cloud wss://*.livekit.cloud`. Регионы облака — другие
   поддомены `livekit.cloud`, поэтому маска, а не один адрес.
5. **Один проект LiveKit Cloud на одно окружение.** Иначе сверка одного
   окружения выведет людей из комнат другого.
6. **Код ядра и клиента не меняется**: имена комнат, токены, перенос
   участника (ADR-0031) и звонки (ADR-0032) работают так же. В облаке есть
   `MoveParticipant`, но перенос остаётся своим, чтобы режимы не расходились.

## Альтернативы

- **Только облако.** Владелец просит сохранить свой LiveKit.
- **Отдельный compose для облака.** Повторил бы основной.
- **Вебхук снаружи всегда.** Подпись защищает и так, но в локальном
  режиме он не нужен, а ADR-0025 его не открывал.
- **Префикс комнат на окружение вместо отдельных проектов.** Менял бы
  имена комнат (ADR-0007) и проверки; отдельный проект проще.

## Последствия

- В облаке есть TURN и регионы LiveKit: звук пройдёт и из сетей, где
  открыт только 443 (на своём сервере TURN выключен, ADR-0033).
- Медиа идут через сервера LiveKit Cloud, за пределами нашего сервера:
  это вопрос к требованиям РФ (docs/legal/russia.md) до беты с чужими
  людьми.
- Облако платное сверх бесплатного объёма.
- Режим cloud в CI не проверяется: нужен проект и его секреты. CI проверяет
  только конфигурацию (compose и Caddy в обоих режимах).

## Пересмотреть, если

- Решим работать только с облаком или только со своим сервером.
- Понадобится несколько окружений в одном проекте Cloud.
- Требования к хранению данных в РФ запретят облако.
