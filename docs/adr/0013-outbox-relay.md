# ADR-0013: Relay outbox → JetStream: порядок и доставка

- Статус: принято; возобновление сессии уточнено в ADR-0016
- Дата: 2026-10-29

## Контекст
ADR-0003 решил, что события пишутся в `outbox` в транзакции изменения и
публикуются в NATS JetStream. Осталось решить, как именно: сколько relay
работает одновременно, какой порядок гарантирован, что будет при падении между
публикацией и пометкой строки, как relay узнаёт о новых строках и сколько
событий хранит стрим.

## Решение
- Relay запускается в каждом процессе с ролью `api`, но работает один:
  каждая пачка берётся под `pg_try_advisory_xact_lock`. Остальные пропускают
  ход. Отдельного выбора лидера нет.
- Пачка до 256 строк `WHERE published_at IS NULL ORDER BY id`, публикация по
  одной с ожиданием ack, потом `published_at = now()` для отправленных. При
  ошибке посреди пачки помечается отправленный префикс.
- `Nats-Msg-Id` = id строки, окно дедупликации стрима 2 минуты. Падение между
  ack и коммитом даёт повтор публикации, который стрим отбрасывает.
- Порядок гарантирован внутри одного сервера: все записи сервера идут под его
  блокировкой (ADR-0012), значит id его событий растут в порядке коммитов.
  Между разными серверами и в `user.<id>` из разных серверов порядок не
  гарантирован, и клиенту он не нужен.
- Пробуждение: `pg_notify('outbox')` в той же транзакции, relay слушает
  `LISTEN outbox`; без уведомлений опрашивает раз в секунду.
- Стрим `EVENTS`, subjects `guild.>`, `user.>`, `channel.>`, файловое хранилище,
  хранение 24 часа. Gateway (шаг 5) возобновляет сессию с номера
  последовательности стрима; кто был офлайн дольше суток, получает полный READY.
- Опубликованные строки удаляются из `outbox` через час.

## Альтернативы
- `FOR UPDATE SKIP LOCKED` и несколько relay параллельно. Быстрее, но ломает
  порядок внутри сервера, а нам важнее порядок, чем пропускная способность.
- Debezium или логическая репликация. Ещё один сервис и слот репликации,
  который надо мониторить; для двух человек избыточно.
- Публикация прямо из обработчика после коммита. Теряет событие при падении
  процесса между коммитом и публикацией.

## Последствия
- Один relay на базу ограничивает поток событий тем, что успевает одна
  горутина с синхронными ack (допущение A12).
- Событие доходит до NATS после коммита с задержкой порядка миллисекунд
  (NOTIFY), в худшем случае через секунду.
- Gateway получает событие хотя бы один раз; дубли вне окна дедупликации
  возможны только при простое relay дольше двух минут посреди пачки.

## Пересмотреть, если
- Задержка от коммита до публикации p99 выше 200 мс или очередь неопубликованных
  строк растёт дольше минуты.
- Больше 5 тыс. событий в секунду: тогда шардировать relay по серверам
  (несколько advisory-ключей по хешу `guild_id`).
