# ADR-0012: Модель сервера и порядок записи

- Статус: принято
- Дата: 2026-10-29

## Контекст
Серверы, роли, каналы и переопределения прав меняются конкурентно: два
модератора одновременно двигают роли, кто-то кикает участника, пока ему выдают
роль. Проверка прав и сама запись должны видеть одно и то же состояние, иначе
появляются окна для повышения прав (выдать роль, которую в этот момент
подняли выше выдающего). Нагрузка на запись в один сервер маленькая: это
действия админов, а не сообщения.

## Решение
- Каждая запись в сервер идёт в одной транзакции: `SELECT … FOR NO KEY UPDATE`
  на строку `guilds`, загрузка ролей и участника, проверка через
  `internal/perm`, изменение, событие в outbox. Изменения одного сервера идут
  строго последовательно. `NO KEY UPDATE`, а не `UPDATE`, чтобы не блокировать
  вставки с внешним ключом на сервер (участники, каналы).
- Роль @everyone имеет id сервера. Позиции ролей непрерывны: 0 у @everyone,
  дальше 1..n. Новая роль встаёт на 1, остальные сдвигаются; перемещение
  сдвигает роли между старой и новой позицией.
- Нет доступа и нет объекта отвечают одинаково, 404. 403 только когда объект
  виден, но действие запрещено.
- События каналов и ролей пишутся в топик `guild.<id>`. Кому из подписчиков их
  отдавать (например, `CHANNEL_CREATE` скрытого канала), решает gateway по
  правам получателя (шаг 5). Личные события (`GUILD_CREATE` при входе, `GUILD_DELETE`
  при кике) пишутся в `user.<id>`.
- Модуль guild читает пользователей только через интерфейс `UserDirectory`
  (реализует `auth.Service`). Внешний ключ `owner_id → users` остаётся: это
  целостность данных в одной базе, а не чтение чужой таблицы.

## Альтернативы
- Оптимистичные версии (`version` в guilds и `WHERE version = $n`). Меньше
  ожидания, но клиенту нужен повтор при конфликте, а выигрыш при нашей частоте
  записи нулевой.
- `SERIALIZABLE` для всех транзакций сервера. Тоже корректно, но ошибки
  сериализации пришлось бы повторять в каждом обработчике.
- Дробные или разреженные позиции ролей (как в Discord, где позиции могут
  совпадать). Проще перестановка, но сравнение «выше/ниже» становится
  неоднозначным, а это основа иерархии.

## Последствия
- Права и запись согласованы без дополнительного кода в обработчиках.
- Медленный запрос внутри транзакции задерживает все изменения этого сервера.
  Внутри транзакции нет сетевых вызовов, кроме Postgres.
- Перестановка роли обновляет до n строк. При лимите 250 ролей это приемлемо.
- Gateway обязан фильтровать события по правам, иначе скрытые каналы утекут.
  Это отдельный пункт чек-листа ревью.

## Пересмотреть, если
- p95 ожидания блокировки `guilds` выше 50 мс (допущение A10).
- Появятся массовые операции (импорт сервера, рассылка ролей тысячам
  участников), которые держат блокировку дольше секунды.
