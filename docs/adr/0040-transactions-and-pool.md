# ADR-0040: Транзакция не ждёт второго соединения

- Статус: принято
- Дата: 2026-11-05

## Контекст
Аудит [2026-11-04](../audit/2026-11-04.md), R1. Внутри транзакций код
обращался к другим модулям: профили авторов (`auth.Users`), упоминания
(`guild.Mentions`), список серверов пользователя. Эти модули читают через
общий пул, то есть берут второе соединение, пока первое занято транзакцией.
Пул по умолчанию — `max(4, NumCPU)`, на VPS с двумя ядрами это четыре.
Четыре одновременных запроса (отправка, вход по приглашению, голос) держат
все соединения и ждут пятое: API стоит, пока не истечёт срок запроса. Таких
мест нашлось больше, чем в аудите: сообщения, сервер и участники, голос,
личные сообщения и группы, профиль, сборщик файлов.

## Решение
1. У `auth.Users` свой маленький пул (`store.Clients.Lookup`, 4 соединения,
   `auth.Deps.Lookup`). Его запросы короткие и ничего не ждут, поэтому
   транзакция, которая ждёт соединение для профиля, всегда его получит.
2. Остальное, что транзакция узнаёт у других модулей, читается до неё:
   упоминания, автор, ответ, список серверов пользователя.
3. Проверки ссылок сборщика (`blob.RefCheck`) читают через его транзакцию
   (`store.DB`).
4. Размер основного пула задаётся явно: `RUSCORD_PG_MAX_CONNS`, по
   умолчанию 20.
5. Тест `TestOneConnectionIsEnough` гоняет основные сценарии с пулом в одно
   соединение. Любое новое второе соединение внутри транзакции даёт таймаут
   запроса.

## Альтернативы
- **Передавать `tx` во все методы чужих модулей.** Пришлось бы менять
  `auth.Directory` и десяток функций с цепочками вызовов, а правило всё
  равно легко нарушить.
- **Только увеличить пул.** Это лишь отодвигает порог: при наплыве
  пользователей зависание повторится.
- **Читать профили до транзакции везде.** В группах и голосе состав
  участников известен только внутри транзакции.

## Последствия
- Процесс держит до 24 соединений с Postgres (20 + 4). Для двух процессов
  стандартных `max_connections = 100` хватает.
- Профиль внутри транзакции читается с другого соединения и видит только
  закоммиченное. Так было и раньше.
- Новые методы, которые другие модули вызывают внутри транзакций, должны
  либо идти через `Lookup`, либо принимать `store.DB`. Нарушение ловит тест
  с одним соединением.

## Пересмотреть, если
- `ruscord_pg_main_empty_acquires` в `/metrics` растёт при обычной нагрузке;
- или растёт `ruscord_pg_lookup_empty_acquires`: четырёх соединений для `Lookup` мало.
