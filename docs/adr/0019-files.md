# ADR-0019: Файлы — аватары, иконки серверов, «о себе»

- Статус: принято
- Дата: 2026-10-30

## Контекст
План `docs/plans/mvp-client-features.md` (шаг 5b-2) включает в MVP аватар,
«о себе» и иконку сервера: клиент `ruscord-fe` их уже показывает. Это первые
файлы, которые присылают пользователи, а загрузки — самое удобное место для
дыры: XSS через SVG или «полиглот», картинка-бомба в несколько КБ на гигабайты
памяти, геолокация в EXIF.

Нужны хранилище с открытой лицензией для self-hosting (MinIO и Garage —
AGPL, см. план), способ удалять старые файлы так, чтобы не ломать открытые у
других экраны, и рассылка изменений профиля по всем серверам пользователя.

## Решение
**Хранилище.** Интерфейс `blob.Store` в `internal/platform/blob`, реализация —
S3 через `aws-sdk-go-v2` с path-style адресами (подходит любой S3-совместимый
сервер). Для разработки и self-hosting — SeaweedFS 4.47 (Apache-2.0,
`weed mini`) в compose; в тестах — `gofakes3` и `blob.Memory`. Без ключей S3 в
dev загрузки выключены (503), остальное работает; вне dev ключи обязательны.

**Конвейер картинки** (`internal/platform/imaging`). Тело до 8 МиБ. Формат по
содержимому (PNG, JPEG, WebP, GIF — первый кадр; SVG и анимированный WebP — 422).
Размеры читаются до декодирования, больше 4096 по стороне — 422. Не больше 4
декодирований одновременно (4096² RGBA = 64 МиБ). Центр кадра вырезается в
квадрат и всегда перекодируется в 256×256: PNG, если есть прозрачность, иначе
JPEG q85. Перекодирование убирает EXIF и всё, что «полиглот» нёс кроме
пикселей. Лимит — 5 загрузок за 10 минут на пользователя (аватары и иконки
вместе, отказы тоже считаются: дорогое здесь — декодирование).

**Ключи и отдача.** Ключ по содержимому: `avatars/<user_id>/<sha256>.<png|jpg>`,
`icons/<guild_id>/...`. В базе хранится ключ, в API — путь `/cdn/<key>`.
`GET /cdn/{key}` отдаёт только ключи этого вида (иначе 404), с `Content-Type`
по расширению, `X-Content-Type-Options: nosniff`,
`Content-Security-Policy: default-src 'none'; sandbox`,
`Cross-Origin-Resource-Policy: cross-origin` и кешем на год (`immutable`):
файл по ключу никогда не меняется. Владелец в ключе разводит одинаковые
картинки разных людей, чтобы удаление одной не задело другую.

**Удаление — сборщик с арендой.** Таблица `blob_garbage(key, delete_after,
lease)`. Загрузка сначала ставит ключ в очередь на час и только потом кладёт
файл: если транзакция, сославшаяся на него, не закоммитится, файл уйдёт.
Замена или удаление аватара ставит старый ключ на сутки в той же транзакции.
Сборщик (`Collector.Run`, раз в минуту на каждой API-ноде) берёт пачку
просроченных строк с `FOR UPDATE SKIP LOCKED`, выдаёт им аренду (новый
`lease`, срок +10 минут), затем по каждой в транзакции: строка с той же арендой
под блокировкой → проверка ссылок модулем-владельцем (`RefCheck`, auth для
аватаров, guild для иконок) → удаление файла, если не используется → удаление
строки. Повторная загрузка того же содержимого сбрасывает аренду, поэтому
сборщик, взявший строку до неё, её пропустит. Вид без зарегистрированной
проверки не удаляется никогда. Удаление сервера ставит его иконку на сутки.

**Рассылка профиля.** Изменение пользователя идёт под блокировкой его строки:
`USER_UPDATE` (полный пользователь) — его сессиям, а если поменялось видимое
другим (`display_name`, аватар) — `USER_PROFILE_UPDATE {user}` с публичным
пользователем в топик каждого его сервера. Иконка — `GUILD_UPDATE` под
блокировкой сервера (ADR-0012), как остальные изменения сервера.

**Gateway.** `USER_PROFILE_UPDATE` пишется в топики серверов без их блокировок,
поэтому отметка снимка (ADR-0016) к нему не применяется, как к сообщениям.
Одно изменение приходит по каждому общему серверу; router отдаёт его один раз
(последний доставленный профиль на пользователя), запись сбрасывается вместе со
статусами при смене состава серверов.

**Уточнение плана.** В плане было `USER_UPDATE {user, profile_version}` в топики
серверов с версией, по которой отбрасывать устаревшее. Версия не нужна:
изменения одного пользователя упорядочены блокировкой его строки, поэтому в
стриме их события идут в порядке изменений. Копия из окна между позицией стрима
и снимком может показать старое значение, но за ней в стриме обязательно идёт
событие изменения, давшего снимку новое, — состояние сходится. Отдельный тип
события нужен, чтобы не путать свои изменения (полный пользователь с email)
с чужими (публичный профиль).

**Просмотр профиля.** `GET /users/{id}/profile` → `{user, bio}` тем, кто связан
с пользователем: общий сервер, общая личка или группа, любая связь со своей
стороны (друг, заявка, своя блокировка) и связь с его стороны, кроме его
блокировки. Остальным — 404, как несуществующему, чтобы не раскрывать
блокировку (ADR-0014).

## Альтернативы
- **Файлы в Postgres (bytea).** Просто, но раздувает базу и бэкапы, а отдача
  идёт через пул соединений. S3 даёт отдельное масштабирование и CDN.
- **MinIO, Garage.** AGPL; MinIO с 2025 года не публикует сборки community.
- **Ключ без владельца (одна копия на одинаковые картинки).** Экономит место,
  но проверка ссылок становится общей для модулей, и удаление аватара одним
  человеком зависело бы от чужих строк.
- **Удаление старого файла сразу.** Ломает картинку у тех, кто ещё не получил
  событие; сутки — с запасом на RESUME и кеш.
- **Удаление без аренды (просто «не используется — удалить»).** Гонка: сборщик
  проверил ссылки, тем временем тот же файл загрузили снова и ещё не
  закоммитили ссылку — сборщик удаляет только что загруженный файл.
- **`profile_version`.** См. «Уточнение плана».
- **Presigned URL и загрузка прямо в S3.** Минует проверку и перекодирование —
  именно то, что делает загрузку безопасной.

## Последствия
- Новый сервис в compose и обязательные ключи S3 вне dev.
- `/cdn` отдаётся с того же домена, что и API; заголовки делают файл инертным,
  но отдельный домен (`cdn.…`) надёжнее — решается к staging.
- Друзья и собеседники вне общих серверов видят новый аватар при следующем
  READY (как в плане); старый URL работает сутки.
- Рассылка профиля — до 100 строк outbox на изменение (лимит серверов), и
  каждое изменение имени или аватара получают все сессии участников его
  серверов, в том числе больших. Частоту ограничивает лимит 10 изменений в
  минуту на пользователя; ленивые списки участников — после MVP.
- Вне dev бакет создаётся заранее (в dev ядро создаёт его при старте,
  SeaweedFS в compose — по `S3_BUCKET`).
- Четыре одновременных декодирования — до ~256 МиБ памяти на ноду
  (допущение A20).

## Пересмотреть, если
- Пиковая память API-ноды на загрузках больше 512 МиБ или p95 загрузки больше
  2 с.
- Очередь `blob_garbage` с просроченными строками растёт дольше часа.
- Появятся вложения в сообщениях: другие размеры, форматы и права на чтение.
