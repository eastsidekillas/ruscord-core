# Чек-лист перед мержем

Не все пункты относятся к каждому PR. В описании PR отмечаем, какие затронуты.

## Безопасность
- [ ] Каждый обработчик проверяет права через `internal/perm`, а не «участник ли он чего-нибудь»
- [ ] Нет IDOR: любой ID из запроса (message, channel, reply_to, invite) проверяется на доступ
- [ ] Права проверяются при каждом использовании объекта (приглашение, ссылка, токен), а не только при создании: права могли измениться
- [ ] Данные о пользователе (имя, аватар, отправитель) ставит сервер, не клиент
- [ ] Секреты не попадают в логи, URL и ответы; ошибки наружу без внутренних деталей
- [ ] Есть лимит частоты для действий, которые можно спамить

## События и состояние
- [ ] Запись в БД и событие в outbox в одной транзакции
- [ ] Событие получают только те, кому положено (фильтр по правам на стороне gateway)
- [ ] Повтор запроса не создаёт дубль (nonce / идемпотентность)
- [ ] Эфемерное состояние в Valkey имеет TTL и восстанавливается после рестарта

## Масштаб и отказы
- [ ] Нет fan-out «всем пользователям» и запросов без LIMIT
- [ ] Что будет, если Valkey, NATS или LiveKit недоступны? Поведение описано
- [ ] Модуль не лезет в таблицы другого модуля

## Решения
- [ ] Если PR меняет решение, есть новый ADR или обновлён статус старого
- [ ] Новые непроверенные допущения записаны в `assumptions.md`
- [ ] Запись в `devlog.md`

## Чистота кода
- [ ] Нет скопированной логики: повторяющийся код вынесен в общую функцию (в пакете или в `internal/platform`), в том числе в тестах
- [ ] Новая функция не повторяет уже существующую (поискать по репозиторию перед написанием)
